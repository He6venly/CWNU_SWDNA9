# 촬영 모드·비용 최적화 명세 검토

2026-10-30. 원문: docs/reference/implementation-plan.v4-v5.md, codex-prompts.v4.md. 원문 속 Phase 실행 지시는 자동 실행하지 않음. 직접 사용자 지시와 아래 정리가 우선.

상태: 검토 완료, 새 계약·기능은 미구현. 현재 코드·테스트·OpenAPI는 기존 1.0.0 기반. 새 촬영 구조는 2.0.0 초안 대상으로 분리하며 현재 스텁이 지원한다고 표시하지 않는 기준.

## 확정 요구와 문서 충돌 해소

| 항목 | 사용자 직접 요구·답변 | 원문 문제 | 정리 |
| --- | --- | --- | --- |
| 촬영 진입 | 전체 짐 / 개별 사진(확대·라벨) 2종 | 원문은 전체 촬영 제외, 개별 라벨/추정만 정의 | 최상위 captureMode는 overview/detail. detail의 식별 방식만 label/estimate로 구분 |
| 최종 판정 | 알고리즘으로 확정, Gemini는 사진 인식·제품 조회에 사용 — 사용자 답변 확정 | 앞선 구현은 Gemini 규정 대조 어댑터 포함 | 새 버전의 evaluate는 순수 규정 엔진. Gemini 결과를 최종 판정으로 사용하지 않음. 기존 Gemini evaluate는 연결되지 않은 이전 준비 코드로 대체 대상 |
| AI 호출 전 | 비용·체감 지연을 줄이는 알고리즘 전처리 | 원문은 주로 리사이즈·Gemini 이후 품질 응답만 포함 | 브라우저의 가벼운 품질·중복·크기 점검을 호출 앞에 추가. 실제 절감량은 측정 후 판단 |

## 촬영 모드 계약 초안

기존 `{airlineId,image}`를 그대로 확정하지 않고 아래 방향으로 변경. 구조 변경이므로 기존 인계 계약 1.0.0을 같은 버전으로 덮어쓰지 않는 원칙.

```ts
type CaptureMode = 'overview' | 'detail';
// overview: 전체 사진 1장, 여러 물품 목록 생성. 작은 라벨 수치는 추측 금지.
// detail: 동일 물품 사진 1~3장. label 또는 estimate 선택.
// mode는 detail일 때만 label/estimate. overview와 별도 모델을 뜻하지 않음.
interface RecognizeRequestDraft {
  captureMode: CaptureMode;
  mode?: 'label' | 'estimate';
  images: Array<{
    kind: 'overview' | 'closeup' | 'label';
    mimeType: 'image/jpeg' | 'image/png' | 'image/webp';
    base64: string;
    cropped?: boolean;
  }>;
  // 개별 정보 보완이라면 기존 물품 id를 연결. 다른 물품으로 값이 섞이지 않게 처리.
  targetItemId?: string;
}
```

- 인식은 항공사에 종속되지 않도록 분리 제안. 항공사를 바꿀 때 재인식 없이 기존 물품을 evaluate로 재판정
- 전체는 items 배열, 개별도 items 배열의 0~1개로 응답 형식 통일 제안. 여러 물품이 찍혔다는 이유의 재촬영 요청은 detail에서만 적용
- 같은 Gemini 모델을 사용하되 모드별 프롬프트·입력 해상도·결과 스키마 제약을 구분. 모드마다 모델 2개를 따로 유지하는 것은 필수 아님
- 전체 사진에서 얻은 물품 id와 개별 라벨 보완의 targetItemId 연결. 라벨만 보이는 사진에서 제품 종류가 자동으로 검증된 것처럼 취급하지 않음
- 이미지별 품질·출처 이미지 연결, 추정 식별·재촬영 안내를 응답에 포함. bbox·크롭 좌표는 원본 기준을 명시해 사진/제품 매칭 유지

## AI 호출 전 최적화 — 제안

권장 순서: 사진 선택 → 헤더 기반 형식·해상도/화소·파일 크기 점검 → 작은 샘플의 밝기·흐림 점검 → 필요 시 재촬영 안내 → 크롭·방향 보정·리사이즈·재인코딩 → 정확한 중복 확인 → 필요한 사진만 Gemini로 전송.

| 처리 | 목적 | 제한·검증 |
| --- | --- | --- |
| 헤더 기반 크기 점검 | 큰 압축 사진을 전체 디코딩하기 전 메모리 위험 감소 | 현재 코드는 디코딩 후 화소를 검사하므로 새 전처리에서 개선 필요 |
| 작은 샘플의 밝기·흐림 지표 | 명백한 실패 사진의 불필요한 API 호출 감소 | 제품·기기별 오탐 존재. 미검증 임계값을 사실처럼 고정하지 않고 안내 위주로 사용 |
| 라벨 영역 크롭 후 해상도 유지 | 불필요한 배경 전송 감소, 작은 문자 보존 | 1280px 일괄 축소로 라벨 문자가 사라지는지 별도 확인. 원본 전체+크롭을 항상 같이 보내지 않음 |
| 압축·전송 크기 관리 | 업로드 시간·실패 감소 | JPEG 파일 용량 감소가 Gemini 토큰/요금 감소를 자동 보장하지 않음. 입력 해상도와 실제 사용량 대조 필요 |
| 동일 사진 재사용 | 같은 요청의 중복 호출 방지 | 단순 perceptual hash 유사도만으로 다른 라벨을 동일 처리하지 않음. 정규화 이미지의 정확한 해시·모드·모델·프롬프트 버전으로 세션 내 재사용 |
| 재판정 분리 | 항공사·제품 값 수정 시 사진 재전송 방지 | evaluate는 규정 버전·항공사·확인된 필드로 계산. 인식 캐시와 판정 캐시 구분 |
| 필요한 경우만 조회 | 모든 물품의 검색 비용·지연 방지 | 모델명 확인·필드 부족·사용자 요청 시에만 lookup 실행. 제공자 실패를 자동 반복하지 않음 |

무거운 브라우저 OCR·물체 탐지 모델·추가 서버 캐시를 기본 구성에 곧바로 넣지 않음. 기기 로딩·메모리·유지보수 비용을 함께 측정한 뒤 결정. 기본 전처리는 Web Worker 또는 충분히 작은 샘플로 메인 화면 응답성을 유지하는 방향.

전처리는 사진 품질·전송·중복 최적화이며, 물품 의미나 위험 여부를 일반 영상 알고리즘만으로 확정하는 기능이 아님. 클라이언트 품질/크롭/해시 표시를 서버 보안 검증의 대체 수단으로 쓰지 않음.

## 기존 명세에서 변경할 항목

| 항목 | 현재 코드 | 새 기준·수정 필요 |
| --- | --- | --- |
| recognize 입력 | 사진 1개 | captureMode, detail 식별 방식, images 1~3개 및 모드별 검증 |
| recognize 응답 | 고정 물품 4개 | 전체 다건 / 개별 0~1개, 품질·재촬영·추정 상태 |
| 필드 | 모델명·수치, 출처 없음 | brand, fieldSources, 식별 방식·추정 후보, 필요 시 전압의 의미 구분 |
| meta | 인식·규정 시연 플래그 | lookup 시연 플래그와 실제 사용 중인 기능 상태 |
| 판정 | 전부 NEEDS_INFO인 스텁 | 검증된 규정 기반 순수 엔진, 추정 제한·조회 확인·계산값 처리 |
| 제품 조회 | /api/resolve-product | 원문 /api/lookup과 이름 통일 필요. 비용 절감을 위해 이름만 바꾸는 별도 API 증식은 피함 |
| 기내/위탁 필수값 | 이미 한쪽씩 분리 | 원문 category 공통 requiredFields로 되돌리지 않음 |
| 무인식 | 200 items:[] | 원문 item:null 성공과 NO_ITEM_DETECTED 오류가 혼재. 200 items:[] + 안내 코드로 통일 제안 |
| 식별 신뢰도 | confidence 값만 있음 | 0.6은 검증된 확률 기준이 아님. 보수적 정책 임계값으로만 정의, 제품 수치의 정확성으로 해석 금지 |
| 폴백 | 실제 공급자 미연결이면 503 | FALLBACK_TO_DEMO 기본 false. 허용해도 demo/fallback 원인 표시, 실측·저장 결과로 혼입 금지 |

## 계산·판정의 안전 기준

- mAh×V÷1000 계산은 같은 배터리의 정격 용량·공칭 전압임이 확인된 경우에만 수행. USB 출력 전압이나 추정 전압을 사용하지 않음
- 원문은 계산값을 소수 둘째 자리로 반올림해 판정하도록 읽힐 수 있음. 판정에는 반올림 전 값을 사용하고, 표시값만 반올림해 경계 반전 방지. 라벨 Wh와 계산 Wh 불일치는 정보 확인 필요
- 계산값을 라벨의 공식 표기와 동일하게 취급하지 않음. 실제 항공사에서 요구하는 확인 방식은 별도 규정으로 판단
- 조건 미확인은 정보 확인 필요로 표현. 의무 정보가 없는 상태를 조건부 가능으로 완화하지 않음
- 독립적으로 확정된 불가는 유지. 추정 정책·낮은 confidence 때문에 불가를 조건부 가능/정보 확인 필요로 덮어쓰지 않음
- 사용자 입력·조회값 확인·규정 버전과 출처를 결과에 연결. 최종 판정은 동일 입력·동일 규정이면 동일 출력
- 실제 규정의 정확성·최신성 검수는 알고리즘·Gemini 사용 여부와 별개로 필요

## 비용·반응성 검증 계획

- 전/후 비교: API 호출 횟수, 이미지 수·전송 바이트, 실제 입력/출력 사용량, 업로드·전처리·AI·전체 지연 분리
- 같은 대표 사진으로 전체/개별/작은 라벨/흐림·어두움/다중 물품/고해상도/중복/다른 라벨의 유사 사진을 대조
- 모바일 실제 기기의 평균·상위 지연과 메모리, 취소·재촬영·UI 멈춤 확인. 목표 수치는 측정 전 임의 확정하지 않음
- 숫자 판독 정확도를 떨어뜨려 얻은 비용 절감은 성공으로 처리하지 않음
- 서버 사진·개인정보 로그 없이 바이트/시간/공급자 사용량 등 최소 비식별 지표만 수집

## 공식 근거·미검증

- [Gemini Media resolution](https://ai.google.dev/gemini-api/docs/media-resolution): 해상도 설정은 토큰·비용·지연·상세 인식에 영향을 줌. 전체/라벨 각각 평가해 설정 선택 필요
- [Gemini 약관](https://ai.google.dev/gemini-api/terms): 무료 서비스의 데이터 처리·민감 정보 제한 확인. store:false와 Google 서비스 전체 데이터 정책은 다른 문제
- [IATA 배터리 안내](https://www.iata.org/contentassets/6fea26dd84d24b26a7a1fd5788561d6e/passengers_travelling_with_lithium_batteries.pdf): Wh 계산은 정격 Ah와 공칭 V 기준. 본 검토가 특정 항공사의 실제 반입 판정은 아님
- 성능 절감률·전처리 임계값·Gemini 실호출·신규 규정 엔진·계약 2.0.0은 아직 구현/측정하지 않음

## 이번 Git 공유 범위

검증된 1.0.0 공통 기반과 본 검토·원문 스냅샷을 별도 개발 브랜치에 공유. 새로운 촬영/판정 명세가 구현된 것으로 표시하지 않음. main 반영 및 프론트의 새 촬영 API 바인딩은 계약 2.0.0 마이그레이션 검증과 구분.
